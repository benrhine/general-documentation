The goal of this page is to capture why things are named as they are along with the reasoning behind it.

Where possible and it makes sense for naming repositories and top level items we want names like the following

== Naming Convention - REQUIRED

Enforcing naming convention ensures DPD repos are easy to find in GitHub and repo scope easily understood.

ids-dpd-dpc-x-y-z

i.e. <organization>-<team>-<project>-<service or library name>

=== Application Services or Libraries

ids-dpd-<project name>-<service or library name>

Example: ids-dpd-dpc-authorization; ids-dpd-dpc-tailored

=== Application Infrastructure

ids-dpd-<project name>-infrastructure

Example: ids-dpd-dpc-infrastructure

=== Application Manifests (For Kubernetes)

ids-dpd-<project name>-manifests

Example: ids-dpd-dpc-manifests

== Property Naming Convention

Aws System Manager Properties should follow the following naming convention ...

/<business-area>/<team>/<account/env>/<tech-framework>/<property-name>

example: /ids/dpd/dev/tf/slack_dpd_dev_aws_dp_alerts_channel_id
